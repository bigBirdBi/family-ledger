**只服务情侣、夫妻和家庭成员的家庭共享账本**。不做公开社区、不做好友动态，也不做复杂的财务系统。核心闭环只有四步：创建家庭、邀请成员、一起记账、查看家庭收支。

## 一、第一版必须有的功能

### 快速记账

首页只保留最常用的操作：

- 输入金额，选择分类，确认即可入账。
- 日期默认今天，付款人默认当前用户。
- 常用分类放第一屏，例如餐饮、买菜、日用、交通、住房、娱乐、医疗、育儿。
- 支持支出、收入、退款三种类型。
- 最近 5 个分类或商家可以快速复用。
- 记录列表支持搜索、修改、删除和按月份筛选。

### 家庭组队

- 一个用户第一版只加入一个家庭账本。
- 家庭创建者是管理员，其他成员是普通成员。
- 管理员生成邀请码或邀请卡片，邀请码设置有效期。
- 对方进入小程序后输入邀请码，完成微信账号绑定。
- 家庭成员可以退出；管理员需要先转让管理权或解散账本。
- 每个成员只能看到自己所属家庭的账本。
- 每笔记录保留“谁记的”“谁付的钱”，便于家庭汇总。

账号绑定本质上就是：**微信 `openid` 与家庭 ID 建立成员关系**。不需要手机号、密码或单独注册。微信目前不能自动读取昵称头像，首次进入时让用户自己设置即可。

### 家庭收支统计

- 首页展示本月收入、支出、结余。
- 按分类查看支出占比。
- 按成员查看本月分别支付了多少。
- 简单月度预算和预算剩余。
- 支持月度账单列表。
- 图表先用 TDesign 进度条和 CSS 柱状图实现，第一版不必引入体积较大的图表库。

“成员支付了多少”适合夫妻和家庭共同管理支出，但不要自动暗示谁应该给谁钱。多人自动分账、分摊比例和结算建议可以放到第二版。

## 二、页面结构

建议只做 5 个页面：

1. **首页**：本月概览、预算进度、最近账单、快速记账入口。
2. **记账页**：大金额键盘、分类、付款人、日期、备注。
3. **账单页**：家庭账单时间线、月份筛选、搜索和编辑。
4. **统计页**：分类占比、成员支付金额、月趋势、预算。
5. **家庭设置页**：成员管理、邀请码、退出家庭、隐私设置。

组件也尽量少：

- 金额键盘
- 分类选择器
- 账单卡片
- 月份切换器
- 成员头像
- 空状态和确认弹窗

这套结构一个人也可以比较快地做完核心闭环。

## 三、轻量级技术栈

### 前端

- 微信原生小程序
- TypeScript
- TDesign Miniprogram
- 原生组件状态管理，不引入 MobX 或 Redux
- 使用 npm 管理依赖，并按需引入 TDesign 组件
- 统计图先用 CSS，后续确实需要复杂图表时再加 ECharts 小程序版

微信原生方案最大的优势是审核兼容性、调试路径短、没有跨端框架运行时成本，适合当前只服务微信的小程序。

### 后端

推荐直接使用 **微信云开发 CloudBase**：

- 云函数：业务接口和权限校验
- 云数据库：家庭、成员、账单、预算
- 云存储：未来存票据图片
- Node.js + TypeScript：编写云函数
- 微信开发者工具负责云函数部署和日志查看

这样可以省掉服务器、域名备案、HTTPS、Redis、Docker 和数据库运维，对家庭级用户量完全够用。

为了后续正式使用，建议把云函数业务逻辑写得相对独立，不把页面直接绑定到云数据库结构。未来如需迁移到自建服务，替换数据访问层即可。

## 四、最小数据模型

只设计四张核心集合：

**users**

- `openid`
- 昵称
- 头像
- 创建时间

**families**

- 家庭名称
- 管理员 `openid`
- 邀请码哈希
- 邀请码过期时间
- 创建时间

**memberships**

- 家庭 ID
- `openid`
- 角色：管理员或成员
- 加入时间

**transactions**

- 家庭 ID
- 记录人 `openid`
- 付款人 `openid`
- 类型：支出、收入、退款
- 金额，以“分”为单位存整数
- 分类
- 发生日期
- 备注
- 创建和修改时间

预算可以放在家庭文档中，例如保存当前月份和预算金额；也可以单独增加 `budgets` 集合。家庭成员数量少，不需要过度拆分。

分类第一版使用固定分类，既方便统计数据，也省掉一套分类管理页面。后续再允许家庭自定义分类。

## 五、云函数接口

保持接口小而明确：

- `login`：获取当前用户资料和所属家庭。
- `createFamily`：创建家庭。
- `generateInvite`：生成限时邀请码。
- `joinFamily`：使用邀请码绑定家庭。
- `getFamily`：读取家庭和成员信息。
- `addTransaction`：新增账单。
- `listTransactions`：分页查询家庭账单。
- `updateTransaction`：修改账单。
- `deleteTransaction`：删除账单。
- `getMonthlyStats`：计算月度统计。
- `saveBudget`：保存家庭月预算。
- `removeMember`：移除成员。
- `leaveFamily`：退出家庭或转让管理权。

所有增删改查都经过云函数，不要让小程序前端直接写数据库。这样可以在服务端统一检查：

- 当前 `openid` 是否属于这个家庭；
- 是否有权限修改这条账单；
- 家庭 ID 是否由服务端确认；
- 删除和成员管理是否符合角色权限。

金额字段使用 `amountCents` 这种整数“分”存储，避免浮点数误差。云函数中永远不能信任前端传来的用户 ID。

## 六、邀请绑定流程

建议采用这个简单流程：

1. 管理员点击“邀请家人”。
2. 云函数生成六位数字邀请码，例如 `482713`，有效期 10 分钟。
3. 管理员通过微信转发邀请卡片，或直接把邀请码发给家人。
4. 家人打开小程序，输入邀请码。
5. 云函数检查邀请码、有效期和当前家庭成员数量。
6. 绑定成功，双方此后看到同一个家庭账本。
7. 管理员可以移除成员，也可以重新生成邀请码。

邀请码不要长期有效，也不要允许同一个码无限加入陌生账号。对家庭记账来说，**限时邀请码 + 管理员可移除**已经足够。

## 七、第一版明确不做

以下功能都建议延后，不要让它们拖慢核心版本：

- 社区、动态、匿名广场、排行榜
- 好友挑战和积分体系
- AI 自动分类和语音记账
- 票据 OCR
- 多家庭账本
- 多币种
- 自动分账和结算建议
- 银行或微信支付自动同步
- 复杂资产、负债和投资管理
- 跨平台 App 或 H5 版本

其中“微信支付自动同步账单”不适合作为初始目标，平台能力和授权限制都比较复杂。第一版只要求用户手动记录，保证每一天真正可用。

## 八、推荐开发顺序

1. 搭好原生小程序、TDesign 和云开发环境。
2. 完成微信自动登录、用户资料和家庭创建。
3. 完成邀请码、成员绑定和家庭权限。
4. 完成快速记账和账单列表。
5. 完成月度统计、成员支付汇总和预算。
6. 补上修改删除、退出家庭、异常状态和真机测试。
7. 最后再处理隐私说明、注销入口和小程序审核。

按照这个方案，第一版不需要额外服务器，也不需要复杂的社交基础设施，重点全部放在“家庭成员打开就能快速记一笔”和“所有人都能看到同一本家庭账本”上。这个范围最适合快速上线，也最符合私人家庭使用的定位。
